# 聊天页面卡片交互需求分析与实施计划

## 1. 概述
本文档旨在梳理AssetFlow聊天页面中各类卡片组件的交互方式，分析当前实现与交互体验最佳实践之间的差异，并制定详细的优化实施计划。

## 2. 卡片分类与交互现状分析

目前聊天页面（ChatPage）主要支持以下几类卡片：

### 2.1 资产类卡片 (AssetCard, ValuationCard)
*   **用途**: 展示用户资产信息（如现金、房产、投资）或房产估值结果。
*   **当前交互**:
    *   **点击 (onTap/确认)**: 发送文本消息 "确认估值 <金额>"。此时会触发AI的一长段回复（"已为您确认...此外..."），比较冗长。
    *   **编辑 (onEdit)**: 点击后弹出一个简单对话框 (Dialog)，用户输入调整后金额。
    *   **提交编辑**: 在对话框确认后，系统自动发送一条文本消息 "用户调整了估值为..."，再次触发AI的重新生成和冗长回复。
*   **问题**:
    *   交互链路冗长：简单的数值修正被转化为"发送消息 -> 后端LLM处理 -> 生成新回复 -> 重新渲染卡片"，导致界面闪烁且产生无意义的对话噪音。
    *   缺乏明确的系统反馈：用户希望"修改成功"这种确定性反馈，而不是AI的唠叨。

### 2.2 行动决策类卡片 (ActionCard, ActionPlanCard)
*   **用途**: 展示系统建议的操作或复杂的行动计划。
*   **当前交互**:
    *   **点击 (onTap)**: 发送文本消息 "告诉我更多关于<建议>的信息"。
    *   **执行 (onExecute)**: 对于ActionPlan，发送 "我决定采纳..."。部分逻辑支持本地状态更新（Checkbox）。
    *   **忽略 (onDismiss)**: 弹出对话框输入理由，然后调用Service接口并更新本地状态。
*   **亮点**: `ActionPlanCard` 已经实现了一定的本地状态管理（展开/折叠、步骤勾选），体验较好。
*   **问题**: `ActionCard` 仍然比较简单，缺乏直接的操作入口（如直接跳转到办理页面）。

### 2.3 产品服务类卡片 (ProductCard)
*   **用途**: 推荐理财产品、保险或服务商。
*   **当前交互**:
    *   **点击 (onTap)**: 发送文本消息 "我对...感兴趣"。
    *   **联系 (onContact)**: 调用系统拨号或发送文本 "我想联系..."。
    *   **购买 (onExecute/Buy)**: 打开外部URL链接。
*   **问题**: 缺乏应用内的详情页，跳转突兀。

### 2.4 数据可视化卡片 (PortfolioChart)
*   **用途**: 展示资产配置饼图/图表。
*   **当前交互**: 点击发送 "请详细解释..."。
*   **问题**: 缺乏图表本身的交互（如点击扇区查看详情、切换试图）。

## 3. 最佳实践差异分析 (Gap Analysis)

| 维度 | 当前实现 (Current) | 最佳实践 (Best Practice) | 差距 (Gap) |
| :--- | :--- | :--- | :--- |
| **交互触发** | **Chat-Driven**: 大多操作转化为发送自然语言文本给LLM。 | **Event-Driven**: 明确的UI事件触发，区分"对话请求"与"功能指令"。 | 当前方式依赖LLM解析，易出错且延迟高；应改为结构化指令。 |
| **数据录入** | **多轮对话**: "我想改价格" -> LLM问"多少?" -> 用户答"500万"。 | **表单/模态框**: 点击编辑直接弹出Bottom Sheet或Dialog进行结构化输入。 | 缺乏高效的数据录入组件。 |
| **状态同步** | **混合模式**: 部分通过WebSocket重推消息，部分本地SetState。 | **乐观更新 (Optimistic UI)**: 操作立即反馈UI，后台异步同步，失败回滚。 | `ActionPlanCard`有尝试，但其他卡片缺乏统一的状态管理机制。 |
| **上下文感知**| 卡片随历史消息滚动，操作可能过时。 | **卡片状态锁定**: 已完成或过期的卡片应置灰或标记状态，防止重复操作。 | 历史消息中的卡片状态管理缺失。 |

## 4. 详细需求梳理

### 4.1 通用交互需求
1.  **结构化事件**: 前端点击卡片按钮时，除发送文本外，应支持发送结构化指令（Payload），让后端精准路由处理。
2.  **表单交互**: 
    *   `ValuationCard` 编辑：点击"修改" -> 弹出底部数字键盘/表单 -> 用户输入 -> 提交 -> 更新卡片显示 + 通知后端。
    *   `AssetCard` 编辑：点击"修改" -> 弹出资产详情表单。
3.  **状态反馈**: 按钮点击后应有Loading状态，操作成功后卡片应变为"已完成/已确认"态，避免重复点击。

### 4.2 特定卡片需求
*   **Asset/Valuation Card (资产/估值卡片)**:
    *   **直接数据同步**:
        *   **确认操作**: 点击"确认"按钮时，直接调用后端 API (`PUT /assets/{id}/confirm`) 更新 `is_confirmed = true`。
        *   **修改操作**: 点击"修改"弹出 Dialog/Sheet，输入金额后，直接调用后端 API (`PUT /assets/{id}` 更新 `value`)。
    *   **UI 反馈**:
        *   前端采用 **乐观更新**，立即更新卡片显示的数值和状态。
        *   在聊天流中，**不**触发新的AI长文本回复。
        *   仅在界面下方显示简短的 System Message 或 SnackBar (e.g., "✅ 资产信息已更新")，或者在聊天流中插入一条极短的系统通知 ("系统：资产估值已更新为 ¥500万")，保持对话干扰最小化。
*   **ActionPlanCard (行动方案卡片)**:
    *   **交互一致性**: 聊天中的卡片交互逻辑应与 `ActionPlansPage` 保持严格一致。
    *   **采纳 (Adopt)**:
        *   点击"采纳" -> 直接调用 `ActionPlanService.adoptPlan(id)`。
        *   成功后，刷新主要 Provider (`actionPlansProvider`) 以确保全局状态同步。
        *   UI 上卡片应立即变为"进行中" (In Progress) 状态，展开步骤列表。
    *   **步骤更新**:
        *   勾选步骤 -> 调用 `ActionPlanService.updateStepStatus`。
        *   **静默同步**: 不发送任何聊天消息，仅在该卡片内部更新进度条和勾选框。
    *   **忽略 (Dismiss)**:
        *   与 `ActionPlansPage` 一致，调用 Service 进行忽略，并允许输入理由。
*   **ProductCard**:
    *   "联系咨询" 优先尝试应用内客服/IM通道，降级为电话。

## 5. 实施计划 (Implementation Plan)

### Phase 1: 交互架构标准化 (Week 1)
*   **目标**: 建立统一的卡片交互Handler，分离 UI 展示与业务逻辑。
*   **任务**:
    1.  重构 `ChatPage` 的 `_handleIncomingMessage` 和 `_sendMessage`，引入 `CardActionHandler`。
    2.  定义卡片交互协议（UI Protocol），例如 `onAction(String actionType, Map payloads)`。
    3.  为所有卡片增加 `status` 字段（active, completed, disabled），历史消息加载时根据状态渲染。

### Phase 2: 引入富交互组件 (Week 1-2)
*   **目标**: 替代低效的对话式修改。
*   **任务**:
    1.  实现 `ValuationEditSheet` 组件（底部弹窗）。
    2.  实现 `AssetEditSheet` 组件。
    3.  改造 `ValuationCard` 和 `AssetCard` 的 `onEdit` 回调，连接到上述Sheet。

### Phase 3: 状态管理与反馈优化 (Week 2)
*   **目标**: 提升操作流畅度与确定性。
*   **任务**:
    1.  全面应用乐观更新（Optimistic Updates）。
    2.  实现操作后的静默数据同步（不产生新的Chat Bubble，仅更新数据）。
    3.  优化 WebSocket 消息类型，支持 `update_widget_state` 指令，允许后端定向更新某条历史消息中的卡片状态。

## 6. 验收标准
1.  点击房产估值"修改"，能直接弹出输入框修改价格，且卡片数字实时变更。
2.  执行Action Plan步骤时，界面无刷新感，且后端数据同步成功。
3.  历史消息中的操作按钮在不可用时呈置灰状态。
